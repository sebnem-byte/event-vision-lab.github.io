A conventional camera integrates light and outputs frames at a fixed rate. An **event camera** instead reports changes in brightness independently at each pixel. An ideal event consists of its pixel coordinates, a timestamp, and the sign of the brightness change:

$$e_k=(x_k,y_k,t_k,p_k), \qquad p_k\in\{-1,+1\}.$$

The resulting stream is **asynchronous**: no event is required when a pixel's brightness remains sufficiently stable.

## 1. Brightness changes, not brightness values

Let $I(x,y,t)$ denote brightness at pixel $(x,y)$ and time $t$. Event-camera models typically operate on *logarithmic brightness*:

$$L(x,y,t)=\log I(x,y,t).$$

For a fixed pixel, when the difference in log brightness since a reference value reaches a contrast threshold $C$, that pixel generates a positive (ON) or negative (OFF) event.

## 3. Event trigger equation

For a single pixel, an event of polarity $p_k$ is generated when the change in log brightness reaches a polarity-dependent threshold:

$$L(x,y,t_k)-L_{\mathrm{ref}}(x,y)\approx p_k C,\qquad p_k\in\{+1,-1\}.$$

In the idealized simulator, the reference is updated in steps of $p_k C$ after each event, so a sufficiently large change can result in multiple events. Practical cameras have threshold variability, noise, latency, bandwidth and refractory-period effects.

## 4. What is special about event cameras?

- **Asynchronous measurements:** individual pixels report independently.
- **Low latency:** events can be timestamped at fine temporal resolution.
- **High dynamic range:** event-camera pixels can work in challenging lighting conditions, subject to the particular sensor.
- **Sparse output:** event generation depends on scene and camera motion, texture and illumination changes.

These are *sensor characteristics*, not guarantees of superior performance for every scene.
